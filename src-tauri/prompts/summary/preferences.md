在生成摘要的同时，检查本次读取的用户原始消息是否包含需要新增、修改或删除的长期偏好或项目准则。偏好用于指导 Agent 今后如何协作、表达和执行后续独立任务；项目准则用于持续约束该项目后续开发中的工作方式、编码与文档规范、验证流程或工程边界。只提取用户明确表达、具有持续适用依据的要求，一条表达一个要求，正文简明、独立、可执行。
先区分“本次要把产品做成什么样”与“今后 Agent 应如何工作”。功能需求、界面交互、数据流程、具体实现方案、功能配置值、性能目标和本次验收条件，默认进入摘要，不提取为偏好。功能实现后会长期存在、用户反复讨论或确认方案，都不能证明它是长期协作准则；“必须、不要、默认、统一、每次、以后”等措辞本身也不能作为准入依据。仅在原始用户消息明确将其作为后续开发中持续遵守的工作准则时，才可提取，并保留原有适用范围。
例如：“新建终端不要触发全来源扫描”“新建会话增加未归属项目选项”“图片粘贴交给 Agent TUI”“首次绑定会话时写入 Workstream”，均是产品行为或实现要求，应留在摘要。“应用生成的摘要最多 2000 字符、使用 Markdown”也是产品提取规则，不是 Agent 日常协作偏好。即使用户说“以后每次新建终端都不要扫描”，仍在描述产品运行行为，不因此变成偏好。
可提取的正例是用户明确作为持续准则提出的“后续修改本项目代码时，注释保持简洁”“今后本项目的 README 更新只保留用途和使用说明”“以后委派 subagent 后等待完成再统一审查，无需频繁询问进度”。同样内容若只针对本次修改、某次审查或当前输出，则不提取；用户直接表达的一贯习惯可以提取，不要求原话必须含有“以后”等特定词。
每次新增、修改或拆分前，内部核对原始用户依据、持续适用性和作用范围：任务完成后，它是否仍是用户要求 Agent 在后续独立任务中遵守的工作准则，还是仅在描述应交付的功能结果？不能把产品需求改写成“开发时应……”来绕过判断，也不能因为现有条目中已有同类产品需求就继续新增、扩写或拆出同类条目。无法明确判断时不变更；核对过程不写入结果。
每条只允许一个可独立执行、修改或撤销的要求，建议不超过 80 字符。修改已有条目也必须遵守：不得将不同规则追加成一段规则集；不同要求必须分别成条。省略背景、理由、实施步骤和摘要本身，保留作用对象及必要条件，例如仅针对本项目代码评审的反馈格式，不能扩大为所有回复的格式。
逐条核对依据必须来自 role=user 的原始消息；role=assistant 的建议、摘要、实测报告及本次提取提示词都不能直接作偏好依据。用户明确采纳某项建议时才可提取，并保留其条件，不能把一句笼统认可扩展为采纳所有细节。没有可确认的原始依据时不变更。
不得仅凭已有摘要推断偏好，不将 Agent 建议、普通事实、当前进度、临时操作或单次任务要求保存为偏好。无法确定长期适用性或作用范围时不新增。
跨项目的习惯和要求归入用户偏好；明确针对某项目的约定归入该项目。不能仅因消息出现在项目内，就提升为用户偏好。只使用输入列出的项目 ID。
已有未锁定条目混合多个要求，且本次原始用户消息能确认各项要求时，应拆分整理：将原条目更新为其中一个要求，其余要求分别新增或复用其他独立条目。不能以“已有混合条目已经涵盖”为由保留规则集；未能核实每项依据时不拆分，锁定条目不拆分。不得仅从现有条目或摘要拆出推测性要求，不在整理时遗漏或扩大原有约束。
对照整理后的独立条目去重，已有独立条目已能表达相同要求时不新增；用户明确补充或纠正已有要求时优先修改。仅在用户明确撤销或明确用新要求取代旧要求时删除，不因未再次提及或不适合当前任务而删除。
保留原有适用条件，不扩大范围，不加入推测。不得新增近义条目变相改写锁定条目，无法消解的冲突不变更。没有符合条件的变更时输出空 changes 数组。
现有偏好仅用于去重、识别变更对象，不作为摘要写作或提取约束，锁定只表示 Agent 不能修改或删除该条目。

新增项目偏好必须同时对照用户级偏好去重；用户级条目已经表达相同要求时，不再创建项目条目。
